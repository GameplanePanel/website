## Invite a local user

Create a unique identity, secure initial credential, and the minimum global role; add per-server collaboration separately.

<DocsSectionList
  items={[
    { icon: "users", label: "Unique Identity", text: "Use a unique username, optional display name/email, and 12+ character password." },
    { icon: "shield", label: "Least Privilege", text: "Assign the minimum required global role; scope server access separately via role bindings." },
    { icon: "lock", label: "Secure Handoff", text: "Send credentials securely (not email) and verify the user signs in privately for the first time." },
  ]}
/>

New users start with a **primary role** applied cluster-wide. The three built-in roles are:

- **Admin** — full access to users, servers, templates, backups, cluster settings, and audit logs
- **Operator** — manage servers and backups; cannot create/edit users or templates
- **Viewer** — read-only access to servers, backups, and status

You can refine permissions per namespace (e.g., restrict an operator to a specific game project) using per-namespace role bindings in the **Role Bindings** section of the user's card. Module and template catalog access is not granted by namespace bindings: it needs a cluster-wide grant on the selected cluster or on all clusters (v0.4.0).

## Edit roles and reset credentials

Role changes affect global authorization; local and OIDC credentials have different owners.

<DocsSectionList
  items={[
    { icon: "users", label: "Role Changes", text: "Edit display name, email, and primary role deliberately — changes apply on the user's next login. Only a full administrator (the wildcard permission) can grant admin-level permissions or edit an administrator (v0.4.0)." },
    { icon: "lock", label: "Local Password Reset", text: "Reset only local passwords in Gameplane with a new 12+ character value; does not affect OIDC users. A reset ends every session of that account (v0.4.0)." },
    { icon: "shield-check", label: "OIDC Management", text: "For OIDC-linked users, manage password, MFA, and account status at the upstream provider (Keycloak, Okta, etc.)." },
  ]}
/>

**To reset a local user's password:**

1. Find the user in the dashboard Users page
2. Click the user card to open details
3. Tap **Reset Password** and enter a new 12+ character value
4. The user can log in with the new password immediately. Every session the account already had is ended, so anyone signed in as that user is signed out (v0.4.0).

**For OIDC users:**

- Password resets happen at the identity provider, not in Gameplane
- MFA and account disablement are provider-controlled
- The user's role and email in Gameplane mirror the provider's state

Users who log in via OIDC have their role determined by:
- **Per-provider role rules** configured under **Admin Settings → Authentication**: an ordered list where the first rule whose group the user is in decides the role (any built-in or custom role), re-evaluated on each login
- **Helm-seeded rules** (`api.oidc.groupsClaim`, `api.oidc.roleRules`, or the older `api.oidc.roleMappings`) for the Helm-configured provider; an admin can override them in the dashboard
- **Manual assignment** when no rule is configured: new OIDC users get the default role (`viewer`) and an admin promotes them

**Roles set by hand stay (after v0.4.3).** Each SSO user's card shows where their role comes from: **From SSO**, **From SSO (applies at next sign-in)** or **Set by hand**. Changing an SSO user's role on the Users page marks it **Set by hand**, and sign-in no longer changes it. To let the rules manage the role again, choose **Return to SSO control** on the user and confirm: the user keeps their role until their next sign-in, when the rule result applies. Local (password) users have no role source. See [Users, Auth & RBAC](../users-auth-rbac/) for how rules are matched.

## Review lifecycle and availability

Audit access changes and remove dormant roles/collaboration; treat service accounts as version-dependent until shipped.

Periodically review:

- **Active users** — remove unused accounts to reduce the attack surface
- **Role changes** — audit the role history in the **Audit & Observability** logs
- **Per-namespace bindings** — clean up stale role bindings if a user's scope narrows
- **Providers** — verify OIDC providers are still responsive; expired provider certificates log an error in the system log
