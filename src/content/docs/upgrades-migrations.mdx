Gameplane releases are pinned with signed container images and strict Kubernetes compatibility. Every upgrade is reversible if planned carefully; every migration is documented in the release notes.

Releases from v0.4.0 are published under `ghcr.io/gameplanepanel`, which this page uses; v0.3.0 and earlier releases stay under `ghcr.io/valgulnecron`.

<DocsCallout icon="refresh-cw" title="Plan platform changes in isolation">
  Do not combine a platform upgrade with unrelated server, storage, authentication, or network changes. Each change introduces risk vectors; combining them makes root-cause analysis impossible when something breaks.
</DocsCallout>

### Export your current values

Before upgrading, save your Helm configuration so you can rollback if needed:

```bash
# Export your installed Helm values (including OIDC, storage, and other overrides)
helm get values gameplane -n gameplane-system > gameplane-values-backup.yaml

# List all installed CRDs
kubectl get gameservers,gametemplates,clusters,backups,modules -A -o yaml > crds-backup.yaml

# Check the current version
helm list -n gameplane-system
```

### Check for breaking changes

Most releases are backward-compatible, but some introduce schema changes or require manual steps. Always check:

- [CHANGELOG](../changelog/) — upgrade notes at the top of the release section
- [Supported Versions Matrix](../supported-versions-matrix/) — which clusters/Kubernetes versions are compatible
- Network changes — if the release adds new `NetworkPolicy` or changes to `spec.networking`
- CRD migrations — if any CRD fields were removed, renamed, or changed in meaning (CRDs are applied automatically by the chart's `crds.autoApply` hook; see [CRD updates on upgrade](#crd-updates-on-upgrade))

### Run the upgrade

Once you have verified your values and backups, apply the upgrade to your cluster:

```bash
# Upgrade to a specific version (e.g., 0.4.3)
helm upgrade gameplane oci://ghcr.io/gameplanepanel/charts/gameplane \
  --namespace gameplane-system \
  --version 0.4.3 \
  --values gameplane-values-backup.yaml \
  --wait

# Watch the rollout
kubectl rollout status deploy/gameplane-operator -n gameplane-system
kubectl rollout status deploy/gameplane-api -n gameplane-system

# Check for errors in operator and API logs
kubectl logs -n gameplane-system deploy/gameplane-operator -f
```

### Observe the cluster

During and after the upgrade, monitor for issues:

```bash
# Watch CRD reconciliation
kubectl describe gameserver <name> -n default  # Check Status and Conditions

# Check API health
kubectl logs -n gameplane-system deploy/gameplane-api --tail=50

# Verify connectivity to pods
kubectl get pods -n gameplane-system
kubectl get pods -n default -l app=gameplane  # Game server pods
```

### Rollback if needed

Only use the rollback procedure if migrations failed or core workflows are broken:

```bash
# 1. Review the release notes for this version's rollback procedure
# 2. Export current CRDs in case you need to debug
kubectl get crds -o yaml > crds-upgrade-state.yaml

# 3. Roll back the Helm chart to the previous version, from the registry that published it
#    (v0.3.0 and earlier: ghcr.io/valgulnecron; later releases: ghcr.io/gameplanepanel)
helm upgrade gameplane oci://<registry>/charts/gameplane \
  --namespace gameplane-system \
  --version <previous-version> \
  --values gameplane-values-backup.yaml \
  --wait

# 4. Verify operator and API pods are running
kubectl rollout status deploy/gameplane-operator -n gameplane-system
kubectl rollout status deploy/gameplane-api -n gameplane-system

# 5. Test core workflows again (create server, check console, etc.)
```

## CRD updates on upgrade

`helm upgrade` never updates CRDs (a Helm limitation: files under a chart's `crds/` directory are installed once and ignored afterwards). The chart works around this with `crds.autoApply` (enabled by default), a pre-install/pre-upgrade hook that runs `kubectl apply --server-side` over the current CRDs. No manual `kubectl apply` step is needed. The hook runs on every `helm upgrade`, and on a `helm install` only when the cluster holds CRDs from a different chart version that an earlier, uninstalled release left behind. A genuinely fresh install never depends on pulling the hook's `kubectl` image.

If you set `crds.autoApply.enabled=false`, apply the CRDs yourself:

```sh
kubectl apply --server-side -f charts/gameplane/crds/
```

- **Helm 3, reinstalling over leftover CRDs:** the hook runs, so air-gapped clusters need `crds.autoApply.image` mirrored for that case.
- **Helm 4:** `crds/` is applied natively with a server-side apply under the field manager `helm`. CRDs last applied by v0.2.0-beta.8 or earlier were applied under the `kubectl` manager, so a Helm 4 `helm install` over such leftovers stops with `conflict with "kubectl" ... .spec.versions`. Re-run it once with `--force-conflicts`:

```sh
helm install gameplane charts/gameplane -n gameplane-system --create-namespace --force-conflicts
```

<DocsCallout icon="info" title="Available since v0.3.0">
The Helm 4 field-manager behavior and the hook-on-reinstall behavior above are part of v0.3.0.
</DocsCallout>

## Upgrading to the next release

The notes below ship in the release after v0.4.3. Read them before you upgrade from v0.4.3.

- **Breaking: the chart installs its CRDs and ModuleSources from hooks.** The packaged chart no longer bundles the `gameplane-crds` subchart. The `crds.autoApply` hook installs the CRDs on every install and every upgrade, so air-gapped clusters must mirror `crds.autoApply.image`. The default and upload ModuleSources are kept across the upgrade and are no longer removed by `helm uninstall`. Turning `defaultModuleSource.enabled` off no longer deletes the existing one. If you set `crds.autoApply.enabled=false`, install the CRDs first from the `gameplane-crds` chart. See [Helm CRD caveat](https://github.com/GameplanePanel/Gameplane/blob/master/docs/install.md#helm-crd-caveat).
- **Breaking: the MCP server no longer reads every namespace.** The break-glass MCP server (`mcpServer.enabled`) no longer has a cluster-wide ClusterRole for Pods, Events and pod logs. The upgrade removes the old `<release>-mcp-server-read` ClusterRole and ClusterRoleBinding. Break-glass reads now cover only the release namespace and the managed game namespaces, through namespaced Roles. A ClusterRole remains for GameTemplate, Module and ModuleSource only. After upgrading, use a personal MCP token (`/users/me/mcp-tokens`) for per-user reads across clusters. See [MCP server (optional)](https://github.com/GameplanePanel/Gameplane/blob/master/docs/security.md#mcp-server-optional).
- **Run `helm upgrade` so each cluster gets its security settings.** Modules can now set the run-as user, run-as group, filesystem group and volume ownership check for their game. Server owners with the `servers:security` permission can override each one, and overrides apply on the next restart. Root overrides are off by default and are allowed per cluster under Clusters, cluster, Configuration, Security. The volume ownership check now defaults to "only when wrong". See [PR #977](https://github.com/GameplanePanel/Gameplane/pull/977).

## Upgrading to v0.4.1 and later

Read the notes for every release between your current version and your target. The full lists are in the [CHANGELOG](../changelog/).

### Release 0.4.1

- **Breaking: native credential boundary (Kubernetes 1.30+).** The chart needs Kubernetes 1.30 or later with ValidatingAdmissionPolicy and PodSecurity admission enabled. Before upgrading, migrate existing credentials, uploads and module locale ConfigMaps, remove legacy service-account token Secrets, and bind each private HTTP or Git module credential to its exact source URL with the `gameplane.local/http-source-url` or `gameplane.local/git-source-url` annotation. Fresh installs enforce Restricted Pod Security on game namespaces; releases upgraded with `--reuse-values` can keep `podSecurity.enforceRestricted=false`. See [native credential upgrade instructions](https://github.com/GameplanePanel/Gameplane/blob/v0.4.1/docs/install.md#upgrading-native-api-credentials).
- **Breaking: game probes are pod-local.** GameServer and GameTemplate HTTP and TCP probes now reject an explicit host. Remove the host from existing probes before the next rollout. See [CHANGELOG 0.4.1](https://github.com/GameplanePanel/Gameplane/blob/v0.4.1/CHANGELOG.md#041--2026-11-17).
- **Breaking: ARK: Survival Evolved module 2.x.** The module runs the community image `hermsi/ark-server` (module 2.0.0) instead of a Gameplane-built image. The data volume moves to `/app`, and cluster transfers move to a second 1 GiB volume at `/cluster`. Schedule downtime and move existing worlds before adopting 2.x, rename `MAP_NAME` to `SERVER_MAP`, and remove `RCON_PASSWORD`. Use 2.0.1 or later. The image starts as root, so it does not run with `podSecurity.enforceRestricted: true`. See [module upgrade steps](https://github.com/GameplanePanel/module/tree/main/ark-survival-evolved#upgrading-from-1x).
- **SteamCMD games need amd64 workers.** The SteamCMD base image is built for `linux/amd64` only. ARK: Survival Evolved, Mount & Blade II: Bannerlord, Nuclear Option, Squad and The Isle now require amd64 workers. On mixed clusters, set the `kubernetes.io/arch: amd64` node selector on affected GameServers that still use older templates. See [affected games and upgrade steps](https://github.com/GameplanePanel/Gameplane/blob/v0.4.1/containers/README.md#platform-support).
- **Live Minecraft Java backups.** Before upgrading agents that only support the v1 backup endpoint, let active live backups finish and check their `Unquiesced` condition. See [operator upgrade guidance](https://github.com/GameplanePanel/Gameplane/blob/v0.4.1/docs/operator-operations.md#shared-operation-ownership).
- **Game worker policy takes over legacy games.** When the new placement and resource policy takes over an existing game, the operator drains its Pod before applying placement and resource changes. A verified running revision uses its saved stop sequence; an unversioned game uses its Pod termination grace. See [CHANGELOG 0.4.1](https://github.com/GameplanePanel/Gameplane/blob/v0.4.1/CHANGELOG.md#041--2026-11-17).
- **PostgreSQL high availability rollout.** To run more than one API replica, first roll out the HA-capable API with one replica and a Secret-backed DSN. After the singleton is ready, enable `api.postgresHA.enabled` and set `api.replicas` to at least `2`. SQLite and standalone installations keep one API replica. See [Helm upgrade instructions](https://github.com/GameplanePanel/Gameplane/blob/v0.4.1/docs/install.md#api-rollout-and-postgresql-availability).
- **SSO usernames are refreshed on login.** Each OIDC login refreshes an existing user's email and display name. SSO users whose username is still the raw subject ID are renamed to their `preferred_username` (or email) on their next login. See [CHANGELOG 0.4.1](https://github.com/GameplanePanel/Gameplane/blob/v0.4.1/CHANGELOG.md#041--2026-11-17).

### Release 0.4.2

- **Breaking: LoadBalancer servers show their hostname as their address.** After upgrading, every LoadBalancer server that already has `spec.networking.hostname` set reports that hostname as its address, in place of the load balancer's IP, once the load balancer has published one. Check that each such hostname resolves to its server before upgrading, or clear it where it does not. See [A hostname as the server's address](https://github.com/GameplanePanel/Gameplane/blob/v0.4.2/docs/networking.md#a-hostname-as-the-servers-address).
- **Breaking: default git module source moves to the v0.4.1 module tag.** This only affects installs that set `defaultModuleSource.type: git`. A git source serves one version per module, so ark-survival-ascended, ark-survival-evolved, minecraft-java, mount-and-blade-2-bannerlord, nuclear-option, palworld, project-zomboid, squad and the-isle change version. Before upgrading the chart, repin each installed Module of these games to the new version, or it goes `Failed` with `VersionUnavailable`. See [CHANGELOG 0.4.2](https://github.com/GameplanePanel/Gameplane/blob/v0.4.2/CHANGELOG.md#042--2026-11-20).

### Release 0.4.3

v0.4.3 is the first published 0.4.2 build. The v0.4.2 tag was pushed, but its release stopped when the image scan found a HIGH vulnerability in the dashboard image, so no 0.4.2 release was published. v0.4.3 ships every 0.4.2 change plus a libxml2 update to the dashboard image. Read the [0.4.2 upgrade notes](https://github.com/GameplanePanel/Gameplane/blob/v0.4.3/CHANGELOG.md#042--2026-11-20) before you upgrade from 0.4.1.

## Upgrade notes for v0.4.0

Read these before upgrading from v0.3.0. The breaking changes come first. The full list is in the [CHANGELOG](../changelog/) under `[0.4.0]`.

- **Breaking: administrator-level grants need `*`.** Holders of `users:manage`, `roles:manage`, `config:manage` or `cluster:manage` without `*` can no longer grant `*` or another admin-level permission, edit or reset an administrator, or edit auth providers. `/admin/config/auth` and `/admin/auth` need `*`.
- **Breaking: kubelet probes reach only probe ports.** A new per-server `<server>-probes` NetworkPolicy admits kubelet CIDRs only to the game container's probe ports. It is on by default through `networkPolicies.probeIngress.enabled`. Set that value to `false` to restore the old all-ports `allow-kubelet-probes` rule.
- **Breaking: custom CSS.** Stylesheets with `\` escapes, absolute `http(s):` references or protocol-relative `//` references are now rejected.
- **Breaking: selected-cluster module and template grants.** In combined and standalone installations, catalog permissions need a cluster-wide grant on the selected cluster or on the wildcard cluster. A grant on `local` keeps local access but no longer authorizes a remote catalog. Before upgrading, grant a role with `modules:read`, `modules:manage`, `templates:read` and/or `templates:write` on each remote cluster, selecting **All namespaces**. See [Standalone panel](../standalone-panel/).
- **Telemetry is on by default for new installs.** A new install with a destination in effect shares basic and extended data once the first admin has seen the first-login notice. Nothing is sent before then. Set `api.telemetry.enabled=false` for a hard off. See [Platform settings, telemetry, and build info](../platform-settings-telemetry/).
- **Existing installs that saved basic telemetry start sending.** An install that turned on **Send anonymous usage metrics** while no destination was configured starts sending basic reports to `telemetry.gameplane.net` after the upgrade. Extended stays off. Set `api.telemetry.enabled=false` before upgrading to prevent this.
- **An empty `api.telemetry.endpoint` now means the project default.** The admin toggles take effect on a stock install. Installs with a custom endpoint or the bundled receiver keep sending only there.
- **Telemetry receiver changes.** The receiver's `/metrics` moved from `:8080` to `:8081` and requires `Authorization: Bearer <DASHBOARD_TOKEN>`. Update Prometheus scraping, or set `api.telemetry.receiver.dashboard.tokenSecretRef.name`. A `DASHBOARD_TOKEN` shorter than 32 characters now stops the receiver at startup. The receiver also stores data by default (`api.telemetry.receiver.persistence.enabled`, 1Gi). `helm upgrade --reuse-values` from 0.3.0 needs no new values: with no `persistence` block the receiver keeps using an `emptyDir`, as before.
- **Password reset ends every session.** Migration `019_session_epoch.sql` runs on API startup. A password reset invalidates every session of that account.
- **Share links have their own Ingress.** `/share` and `/shares` go through a second Ingress, `gameplane-share`, with access logging off for ingress-nginx. Other controllers need their own switch in `ingress.shareLinks.annotations`.
- **The API is a singleton.** Every database driver uses the `Recreate` strategy, and `api.replicas` values other than 1 are rejected.
- **Standalone panel.** The central panel can now run with Docker Compose or the standalone Helm profile, without a local game cluster or operator. Register remote clusters explicitly, and back up the database and its matching credential encryption key separately. When migrating a legacy `/data/panel.key` installation, keep the original key. See [Standalone panel](../standalone-panel/).
- **Game and auxiliary pods can restart.** Agent, config-init, sentinel, tunnel and Restic pods now request resources on every install. Upgrades can restart game pods or leave them Pending when capacity is short. See the [v0.4.0 operational notes](https://github.com/GameplanePanel/Gameplane/blob/master/docs/release-notes.md).

## Upgrade notes for v0.3.0

Read these before upgrading from v0.2.0-beta.8:

- **Every existing GameServer rolls once.** Network capture needs a pre-provisioned volume on every game pod, because Kubernetes ephemeral containers can add containers to a running pod but not volumes. The capture `emptyDir` is therefore added to every pod template, and each pod is recreated once on upgrade, interrupting active player sessions. This does not repeat on later starts. Servers that do not opt into capture carry only an empty, unused volume: no capture sidecar, no `CAP_NET_RAW`, no network change. Plan the upgrade window accordingly.
- **Owner-only server operations.** Transferring ownership, editing collaborators, wiping data and deleting a server now need the server's owner or an admin. Operator-role users keep their other server permissions but can no longer run these four operations on servers they do not own. Servers with no recorded owner (for example created with kubectl or GitOps) can be transferred, wiped or deleted only by an admin.
- **Playit tunnel egress widened.** The operator-managed NetworkPolicy for a GameServer using the `playit` tunnel provider now adds an unrestricted egress rule (all ports and protocols, any destination) alongside the DNS/advertised-ports rule every provider gets. Previously playit could not reach its relay.
- **Helm 3 and Helm 4 CRD handling.** See the section above, including the one-time `--force-conflicts` for Helm 4.
- **Tunnel credential Secrets must be owned by their GameServer.** The operator refuses a tunnel credentials Secret whose `ownerReference` does not match the GameServer's name and UID, scales the tunnel to zero and reports `TunnelReady=False` with reason `TunnelCredentialRefused`. Secrets created with plain `kubectl create secret` for v0.2.0-beta.8 are refused after the upgrade: re-enter the credential in the server's Networking tab (which writes an owned `<server>-tunnel-auth` Secret) or add the ownerReference. See [Server Networking & Tunnels](../server-networking-tunnels/).

## Rollback decision

Close the rollback window only when:

- **Data integrity verified:** All CRD records migrated cleanly (check `kubectl describe` for migration errors in Conditions).
- **Workflows tested:** Logged in, created a server, ran console commands, verified backups and authentication.
- **Version recorded:** Note the new version in your runbooks and team docs so you can rollback to the exact prior version if needed in the next 24 hours.

Once 24 hours have passed without issues, backups of the pre-upgrade state become less relevant (newer backups have accumulated). At that point, safely delete old backup snapshots to reclaim storage.
